# ADR-003 — Аутентификация по статическому API-key (X-API-Key)

- Статус: Accepted
- Дата: 2026-06-09

## Context

Сервис автономный, вызывается доверенной внешней системой (не конечными пользователями напрямую). Пользователь зафиксировал доступ по `API_KEY` из `.env` в заголовке `X-API-Key`. Нужно зафиксировать схему и требования безопасности.

## Decision

- Единый сервисный ключ `API_KEY` из `.env`, передаётся клиентом в заголовке `X-API-Key`.
- Проверка ключа выполняется в зависимости FastAPI (dependency) на всех роутерах `/api/*`.
- Сравнение — **constant-time** через `secrets.compare_digest`.
- `GET /health` — без ключа (для healthcheck оркестратора/балансировщика).
- Нет per-user идентичности; «пользователь» в ТЗ — это логический владелец треда, разграничение прав между пользователями не реализуется (v1).

## Consequences

- (+) Простейшая модель, соответствует автономности сервиса и NFR простоты.
- (+) Нет инфраструктуры выпуска/валидации токенов.
- (−) Один ключ на всех клиентов: нет гранулярного отзыва. Ротация — заменой `.env` и рестартом.
- (−) Нет rate limiting per-key (TD-002).

## Alternatives

- **JWT / OAuth2** — отвергнуто: нет пользователей и identity-провайдера; избыточно для автономного сервиса.
- **mTLS** — отвергнуто: усложняет интеграцию клиента; TLS терминируется на reverse-proxy.
